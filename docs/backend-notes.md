# Phase 1 backend notes

- **The seam:** `src/app/(app)/studio/actions.ts#generateDraft` is demo-only today. To go live, have it call `src/lib/ai/generate-content.ts#generateContentDraft({ orgId, businessBrain, prompt, format, platforms })` first; a `null` return means "not configured or couldn't parse" — fall back to `pickCannedDraft(...)` exactly as now. Same pattern for images: `src/lib/ai/generate-image.ts#generateImage` returns `null` when `FAL_KEY` is unset.
- **Quota errors are not demo fallbacks:** both functions above *throw* `AllowanceDeniedError` (`src/lib/ai/errors.ts`) when the org is out of quota/spend cap — catch that in the server action and show a real "you're out of quota" message, don't swallow it into a demo draft.
- **Persistence:** once a draft is accepted, use `src/lib/content.ts` (`saveContentItem`, `rateContentItem`, `saveTemplate`, `listTemplates`, `queueContentItem`, `listScheduledItems`) for all reads/writes — all RLS-scoped, all demo-safe (return `null`/`[]` when Supabase isn't configured).
- **Applying migrations:** once real Supabase keys exist in `.env.local`, run `supabase db push` (or paste `supabase/migrations/0001_foundation.sql` then `0002_content.sql` into the SQL editor, in order — both are safely re-runnable).
- **Model routing + cost table:** the *only* place OpenRouter model ids and $/Mtok pricing are pinned is `src/lib/ai/router.ts` (`MODEL_CANDIDATES`, `MODEL_PRICING`). The fal.ai per-image cost is pinned in `src/lib/ai/generate-image.ts` (`COST_PER_IMAGE_USD`). Update pricing there if a route changes.
- **Env vars used:** `OPENROUTER_API_KEY`, `FAL_KEY`, `NEXT_PUBLIC_APP_URL` (all already in `.env.example`) — nothing new to add.
- **Slideshow rendering (the "video" format):** `src/lib/media/slideshow.ts#renderSlideshow` shells out to the system `ffmpeg`/`ffprobe` binaries (args array only, no shell interpolation) to assemble 3-5 images into a 1080x1920 MP4 with Ken Burns zoom + crossfades, no audio track yet (see the `-an` TODO in that file for where a licensed music bed would get mixed in). Files render into `os.tmpdir()/localos-slideshows/<uuid>/` and are streamed back by `src/app/api/slideshow/[id]/route.ts`; `src/app/(app)/studio/actions.ts#renderSlideshowAction` is the server action the Composer calls, and it's metered against the org's `slideshows` allowance exactly like images.
- **TODO — "media" Storage bucket:** once Supabase is configured, `src/lib/content.ts#saveSlideshowMediaAsset` best-effort-uploads the rendered MP4 to a Supabase Storage bucket named `media` and writes a `media_assets` row. That bucket isn't provisioned by any migration yet — create it (Storage → New bucket → `media`, decide public vs. signed URLs) before relying on this path; until then the upload silently no-ops and the slideshow still plays fine from the local temp-file route.

# Phase 2 backend notes

- **The seam:** the Unified Inbox / FrontDesk / CRM UI (`src/app/(app)/inbox`, `src/components/inbox`) should read/write exclusively through `src/lib/frontdesk.ts` — `listConversations`, `getConversation`, `sendMessage`, `setConversationStatus`, `setAiState`, `listContacts`, `getContactWithTimeline`, `upsertContact`, `updateContactStatus`, `createAppointment`. Every function is RLS-scoped (uses the per-request server client, not the admin client) and demo-safe: each returns `null`/`[]` when Supabase isn't configured, so a server action can call it unconditionally and fall back to `src/lib/demo.ts` (`DEMO_CONVERSATIONS`, `DEMO_CONTACTS`, `DEMO_APPOINTMENTS`) exactly like `src/app/(app)/studio/actions.ts` does for Content Studio.
- **AI drafting:** `src/lib/ai/frontdesk-reply.ts#draftCustomerReply({ orgId, businessBrain, conversation, messages, contact })` drafts the next customer-facing reply. It routes through `runTextJob("customer_reply")` (`src/lib/ai/router.ts`), which is pinned to **Claude Haiku 4.5 first** — do not repoint this job at a free-tier model, this prompt carries real customer PII (MASTER_PLAN §5). It's metered against the org's `ai_replies` allowance automatically via `runTextJob`. Returns `null` when OpenRouter/Supabase aren't configured or the model can't produce valid JSON after one retry — the demo fallback for an `ai_state: "ai_draft"` thread is the conversation's own canned `pendingAiDraft` string in `src/lib/demo.ts` (a demo-only field, not a DB column — see the `DemoConversationDetail` type). `AllowanceDeniedError` is *not* swallowed here — same pattern as `generate-content.ts`, surface a real "out of quota" state.
- **Migration `0003_frontdesk.sql`:** adds `contacts`, `conversations`, `messages`, `appointments`, all RLS-scoped to `private.user_org_ids()`, same conventions as `0001`/`0002` (re-runnable, owner/admin-only deletes, `private.set_updated_at()` triggers). `contacts` has partial unique indexes on `(org_id, phone)` / `(org_id, email)` (only enforced when that field is non-null). `messages` has no `updated_at` — it's an append-only ledger like `usage_events`, with `select`/`insert` policies for `authenticated` org members only (no `update`/`delete`).
- **Webhook ingestion — TODO (Phase 2 channel connections):** inbound messages from real channels (web chat widget, SMS via Twilio, email via Resend/Brevo inbound parse, IG/FB Messenger, missed-call-to-text) aren't wired up yet. When building each channel connector, insert inbound `messages` rows (and `contacts`/`conversations` as needed) via the **service-role admin client** (`src/lib/supabase/admin.ts#createAdminClient`), which bypasses RLS entirely — webhook requests aren't authenticated as an org member, so they can't use the RLS-scoped client `src/lib/frontdesk.ts` uses. Keep the insert shape identical to what `sendMessage` produces (`direction: "inbound"`, `kind: "message"`) so `frontdesk.ts` reads work unchanged. After inserting the inbound message, call `draftCustomerReply` and either auto-send via `sendMessage` (→ `ai_state: "ai_answered"`) or leave it for owner review (→ `ai_state: "ai_draft"`), matching the three named AI-transparency states in `docs/design-briefs/phase-2-inbox-frontdesk-crm.md`.
- **Env vars used:** no new ones for this migration/data layer — `OPENROUTER_API_KEY` is reused for `customer_reply`. Webhook connectors (future work) will need `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_PHONE_NUMBER` (SMS/missed-call-to-text) and `RESEND_API_KEY` (email) — already present in `.env.example`.
